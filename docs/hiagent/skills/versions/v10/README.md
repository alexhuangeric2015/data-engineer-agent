## 部署

1. 在测试智能体中使用本版主提示词三选一，并选择对应执行模式；整段替换，不叠加旧主提示词。
2. 注册一个 `data-asset-query`，上传整个技能目录并保留相对路径。`data-asset-query.zip` 是该目录的普通 ZIP 传输包，包含根目录 `data-asset-query/`；不是已确认适配某版 HiAgent 的专有导入格式。不接受 ZIP 时，按平台支持方式上传目录及附属文件。
3. 在测试智能体中解除旧四个 SKILL 的绑定，以免模型仍走旧入口；保留旧智能体/文件用于对照，不删除旧版本。四份参考无需另行注册。
4. 保留真实知识库检索和数据库工具绑定；原工具若依赖旧 SKILL 附带配置，需要将实际工具权限/绑定配置到新入口可用的位置。注册一个 Markdown 包不自动迁移这些配置。不要因为解绑旧技能而移除底层 KB/DB 工具。
5. 不把 references 上传进业务知识库作为替代；不上传本 README、检查脚本或验收数据为运行知识。

本轮只生成本地交付物，没有操作你的 HiAgent 实例或生产数据。

## 必须先确认的包读取能力

此设计依赖 HiAgent 保留技能附属文件并允许按相对路径读取；此前无法指定读取某个业务知识库文件，不足以证明技能附属文件也不支持。当前也没有证据证明附属读取已可用。

在测试智能体上先完成一次真实验证：加载 `data-asset-query` 后，是否能读取 `references/table-schema-kb.md`，并在准备进入结构 DB 时读取 `references/table-schema-db.md`。再用独立字典请求验证另外两份。优先检查文件读取日志/实际载入内容；没有可见证据就记录能力未验证，不能仅凭模型声称“已读取”判定通过。这是内网人工验收步骤，不要求每次用户查询都先读完四份。

若平台自动把所有附属内容一次注入，可使用实际已加载内容，但不要宣称实现了按需加载或减少上下文；若平台完全不支持读取附属文件，本包在当前形态不可运行。运行正文遇到必需参考无法读取时结束受影响分支、保留成功项并说明资料加载问题，不反复猜路径、不转到旧技能或 KB 搜文件。届时应依据实际能力另做单文件部署版，不在本轮假装文件已可读。

主提示词引用 `data-asset-query` 也不自动生成函数；按平台真实技能绑定使用。如果界面要求可视化引用，使用照片所示的技能选择入口选中实际注册项，不编造调用名称和参数。独立 Planner/Executor 模型提示词注入、上下文共享、工具内部重试与分页均沿用实际平台契约，不因目录结构变化就视为可用。

## 按需加载与查询顺序

| 当前任务/证据 | 加载参考 | 后续实际动作 |
| --- | --- | --- |
| 新表或字段目标 | table-schema-kb.md | 用结构 KB 发现相关标识 |
| 结构候选可核验 | table-schema-db.md | DB 核验表身份，确认后在表内精准查字段 |
| 新独立字典目标，或结构字段已确认且有代码名称 | dictionary-kb.md | 用字典 KB 发现类型线索 |
| 字典候选可核验 | dictionary-db.md | DB 核验类型，确认后精准取明细及 SQL 统计 |

已确认父对象内成员复用有效定位；不是每次查一个值都加载四文件、重查两类 KB。读取文件不算查询数据库。引用链的下一阶段仍由同一入口判断，没有子代理或递归调用。

KB 无标识结束分支；近似、版本相似及同名冲突等待用户确认；上游失败/待选不进入下游。枚举与指定值、集合与单目标歧义继续区分。SQL 明细及统计九个模板原样迁移，保留配对、原范围、原始记录/重复、N/M/P/R/D 页脚、限行纠正与停止、普通续问及显式刷新合同。

预算仍为每回合结构/字典 KB 各一次、DB 合计八次，身份定位分支三次，同父成员补查一次，每结果集计数一次/修正合计一次/五数据页；都只是文字约束，未设置平台硬门禁。参考读取/技能加载与 KB/DB 实际调用分别统计。KB 无多查询能力时如实记录各目标覆盖，不把拼接关键词当成独立查询覆盖。

## 本地检查与内网验收

仓库根目录运行：

```bash
rtk proxy python3 -B docs/hiagent/versions/v10/check_contracts.py
```

检查脚本在技能包之外，复用同仓库 V8 隔离数据及判据，不需要连接内网。它验证唯一入口、参考路径、模式正文一致，并实际执行本包内九个 SQL，检查原名称范围、配对、反查、前导零/空值、冲突、重复明细及类型总量与指定值数量。它不能证明 HiAgent 真实加载和模型行为。

本轮已尝试 skill-creator 的 `quick_validate.py`，但本机两套 Python 均缺少 PyYAML，因此该通用验证器没有运行通过；未为文档改造安装新依赖。本版检查脚本覆盖本包实际使用的两个单行 frontmatter 字段、名称/描述及包结构，不把它说成完整 YAML 验证器，也不继承其他技能系统的可选字段或安装策略。

内网沿用 [V8固定任务](../v8/eval_cases.json) 与 [V9对照方法](../v9/README.md)，另重点检查：

- 新入口确实生效，旧四技能不再被路由；应进入的参考可读，不需要的分支没有额外读取。
- 表字段请求与独立字典/码值请求入口正确，实际 KB→DB 顺序与父对象确认正确。
- 缺文件、无召回、DB 错误、待选择及实际限行分别正确结束，不重新定位；技术失败不会要求用户换业务名称。
- 统计及逐行原始展示与原方案一致，未把身份定位当成完成，重复行和同码异义没有被合并。
- 文件读取次数、真实 KB/DB 调用、模型调用、结果完整性与耗时分别记录，不预先承诺本版提速。

先以同一模式对照 V9 与 V10，判断技能组织变化；再在 V10 内比较三种模式，避免同时改变模型、模式和技能后无法归因。这个顺序是测试建议，不是已运行的评测。
