# 企业数据智能体规划方案编写原则

确认日期：2026年10月28日。

## 目标：有高度，也有细节

方案应同时支撑领导决策和专业审阅。高度体现在建设必要性、企业定位、整体架构、长期能力与推进取舍；细节体现在模块建设、内部机制、数据流转、平台交互、实施依赖、责任及完成证据。不能用抽象概念代替建设内容，也不能用实现清单代替整体规划。

全文和图集沿同一条逻辑链展开：

**业务目标 → 赋能场景 → 能力与架构 → 模块建设 → 工作机制 → 阶段成果与收益。**

每项重要建设内容都应向上对应业务目标和场景，向下对应具体模块、依赖、责任与可验证成果。

## 需要回答的问题

| 层面 | 必须讲清楚的内容 |
| --- | --- |
| 建设判断 | 为什么值得建设；不建设会保留哪些问题；为什么选择该切入点和推进顺序。 |
| 企业定位 | 在企业数据体系中的位置；与HiAgent及现有平台的边界；优先复用与需要补强的部分。 |
| 能力与架构 | 面向哪些角色和任务；三类九种专业角色如何组合；内容、工具和执行平台如何支撑。 |
| 模块建设 | 建什么、形成什么内容或服务、谁维护、依赖什么；不能只罗列“指标库、知识库、规则库”。 |
| 内部机制 | Agent如何理解、规划、检索、消歧、查询、调用和验证；数据如何加工、更新并返回结果。 |
| 实施路径 | 难点、前提、风险、责任、分期与完成标志；不把模型可生成或接口接通等同任务可用。 |
| 价值证据 | 交付成果如何改善业务；案例方法如何迁移；怎样用真实任务基线和业务采纳验证收益。 |

## 指标模块示例

不能只写“建设指标库，统一口径，赋能分析”。需要把以下内容连接起来：

1. **业务问题**：同名不同义、重复定义、重复开发、报表与问数结果不一致，分别影响哪些业务场景。
2. **建设内容**：定义、公式、粒度、维度、过滤条件、适用范围、物理实现、版本、生效期与责任；区分定义管理与计算服务。
3. **平台分工**：优先盘点并复用资产或指标平台，补强语义、映射、接口、审核或消费闭环，不默认再建一个权威中心。
4. **工作机制**：Agent查定义和实现、澄清歧义、选择维度、调用受控计算；依据真实结果返回来源和限制。
5. **建设顺序与难点**：从高价值、口径可确认的核心场景开始；解决历史口径、实现一致性、责任确认及版本同步。
6. **价值验证**：观察审核指标复用、重复建设、口径争议、结果一致性及业务采纳，不移植外部案例收益数字。

其他模块应达到相同深度，并根据职责采用合适的图解。

## 图文表达与版本基准

- V0.3能力全景是用户明确认可的结构基准，保留六层主体、专业角色及职责、内部运行机制、HiAgent支撑列、贯穿保障列和血缘调用链。
- 架构图必须表达包含、分工、依赖或流转关系，不能将功能清单装入等权方框后当成架构。
- 能力图、功能图、系统架构、数据流、概念数据模型、集成和部署视图各回答不同问题，不能仅更换标题。
- PPT用于汇报讲述，draw.io用于完整架构审阅；分别设计并保持一致，不再从压缩PPT页面直接生成独立详图。
- 场景图同时体现处理链路、解决问题和应用价值。视觉表现服务于业务和架构理解，不削减必要内容以追求整齐。
- 正文体现机制、难点和系统分工，不另设技术备答章节。预算与测算由甲方自行规划，不纳入本材料。

## 已确认的架构边界

当前仅建设数据资产智能体及其配套资料治理；其他能力属于规划。专业Agent内部规划，可按需引用其他Agent；SKILL定义规则与方法，由Agent实际引用和调用资源。

当前查询采用知识库定位候选、外部结构化数据库核验表字段及字典码值事实。实际血缘经数据资产平台查询；业务语义、字段字典映射、逻辑关联与真实加工血缘分别表达。系统与平台包括开发、资产、调度、血缘、质量及数仓计算等能力，原平台保留权威事实及执行责任。

部署采用逻辑规划视角，不能把未确认的网络、机器、模型位置或部署方式写成现状。案例需可追溯，区分公开披露、规划假设和项目事实，不虚构收益、成熟度、上线或验收结果。
