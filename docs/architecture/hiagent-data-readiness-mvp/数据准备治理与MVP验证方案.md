# HiAgent 数据准备、治理与 MVP 验证方案

日期：2026-10-21。独立讨论与执行准备稿。沿用此前 H1—H4、B1—B5 模块命名；不修改原架构图、HiAgent 运行配置或 SKILL。涉及数量、容量和验收比例均为建议，尚无内网实测成绩。

## 1. 要增加一条“业务知识和数据准备”工作线

只有表结构，可以知道字段存在，却无法充分判断一行数据表示什么、哪个时间用于统计、退款是否冲减、余额是否可跨日求和。客户六项能力需要的不只是检索能力，还需要经过责任人确认的业务定义、技术映射和运行证据。

建议两条工作线共同推进：

- **资料与治理线**：选场景、确定责任人、收原材料、预填模板、澄清口径、技术核验、确认发布、变更维护。
- **HiAgent 与工程线**：接知识检索与事实查询、设计场景 SKILL、接检查和测试工具、记录成果版本、执行评测。

治理首期只做到“选定场景有可信依据”。不先建设全企业统一数据标准、主数据平台或完整治理产品，也不等所有系统资料齐全再开始验证。

## 2. 没有模型库、指标库、术语库时怎么处理

| 缺失对象 | 从哪里找原材料 | 项目组做什么 | 谁确认 | 最小交付 |
|---|---|---|---|---|
| 业务术语 | 报表名称、业务制度、需求文档、页面说明、专家访谈 | 整理定义、别名、适用范围、反例和关联资产 | 业务口径责任人 | 可检索的已确认术语清单 |
| 指标 | 常用报表、计算Excel、存量SQL、需求与对账结果 | 形成业务口径和技术实现两份记录，列出分歧 | 业务确认定义，研发确认实现，二者冲突交业务裁决 | 少量版本化指标定义及来源映射 |
| 数据模型 | 现有表、ER图、作业SQL、报表加工逻辑 | 先登记业务实体、表粒度、主键和关系；再对目标需求提出模型 | 数据架构/数仓负责人和业务责任人 | 现状模型登记或新建模型草稿，注明对象性质 |
| 质量规则 | 现有校验SQL、业务异常、报表对账、缺陷记录 | 转成规则对象、执行范围、阈值依据和预期结果 | 业务确认正确性边界，研发确认可执行性 | 本场景必要规则与可执行校验 |
| 调度与故障知识 | 作业导出、实例日志、告警、处置工单 | 整理真实依赖、周期、故障证据与处置限制 | 平台/运维负责人 | 后续调度和诊断试点资料 |

指标与模型的结构化定义可以先保存在受控版本文件或现有资产系统，提供精确读取能力；并不要求立即采购一个“指标库产品”。有正式平台后按稳定ID和版本迁移。语义建模至少需要明确实体、维度和时间等概念，可参考 [dbt 语义模型](https://docs.getdbt.com/docs/build/semantic-models)；本项目不直接照搬其 YAML 作为 HiAgent 导入格式。

**旧SQL也是证据，不是绝对真理。** 它可能有历史缺陷；业务定义、实现和实际结果不一致时，先建问题单，不能让模型静默选一个。余额、比率、去重人数等必须说明可加性和聚合边界，不能默认所有数值都可SUM。

## 3. 如何组织各业务系统提交

### 3.1 每个试点系统需要明确三个责任角色

| 角色 | 要提供和确认什么 | 项目组如何降低其工作量 |
|---|---|---|
| 业务口径负责人 | 指标目的、术语、统计对象、排除规则、时间、单位和预期结果；跨部门分歧的裁决人 | 先拿现有报表访谈，由项目组预填，业务只确认差异 |
| 系统研发/数据负责人 | 表字段、粒度、关联、字典、历史数据、存量SQL、变更及技术映射 | 自动导出已有结构，保留原标识，只让其补缺失业务说明 |
| 平台/运维联系人 | 数据权限、目标引擎、测试环境、作业依赖、日志、接口与资源限制 | 提供导出清单、接口清单和测试所需条件，不要求手工复述所有平台配置 |

一个人可以兼任，但每项正式定义都要有可追责确认人。业务跨系统时，客户项目负责人指定最终口径裁决人。没有裁决责任人，增加模型或向量库无法解决同名异义。

### 3.2 推荐收集流程

1. **客户项目负责人发起**：只列一个试点业务域、一个报表/指标场景、涉及系统、资料负责人和约定提交时间。项目组不擅自向他人发送材料。
2. **先收原件和导出**：DDL、字典CSV、存量SQL、报表样张、需求/制度、预期结果；不要让所有人先填完整模板。
3. **项目组预填**：技术结构由导出预填；文档/SQL可由模型辅助抽取成草稿，每项保留原文件、页节/SQL位置和版本。推断单独标注。
4. **分角色确认**：技术人员核验存在性及映射，业务人员确认口径；一次只追问影响当前场景的关键缺口。
5. **检查与退回**：查必填、ID引用、范围、版本、口径冲突和样本一致性；把问题分派给具体责任人。
6. **发布一个资料版本包**：已确认且适用的定义进入正式查询；草稿、冲突和过期版本不能冒充当前事实。平台不能按状态过滤时，使用独立已发布知识库/文件集合，而不是仅提示模型忽略草稿。
7. **持续维护**：表或SQL变更、制度变更和口径调整触发影响检查；原记录保留失效时间及替代版本，重新运行受影响评测。

术语的别名、上下位关系、责任人及审核可以参考 [OpenMetadata 术语治理](https://docs.open-metadata.org/latest/how-to-guides/data-governance/glossary)。本方案复用这些治理原则，不要求首期部署该产品。

### 3.3 提交和治理状态

建议记录：草稿、待确认、已确认、冲突、已失效；正式发布另外记录发布批次和有效期。已确认不是自动执行授权，已发布不是允许任意用户访问。

“已确认”须有关联责任人、时间、来源与定义版本。Excel里的状态只是收集信息，不能直接成为系统授权或跳过审核。导入服务核验确认记录、权限和ID引用后，才能将其用于对应范围的正式查询。未知保留空值并登记问题，不用0或自行推断值填满模板。

## 4. 收集模板包：谁填哪些

配套工作簿按不同对象拆表；第7行为虚构示例，正式提交前删除，第8行起填写，原样ID/码值按文本保留前导零。数据日期使用真实日期类型。字段说明集中在工作簿末页，模板列的“条件必填”按对应说明判定。

| 工作表 | 主要提供方 | 本次MVP用途 |
|---|---|---|
| 系统与人员 | 系统负责人 | 系统范围、业务/技术/平台责任人 |
| 表业务说明 | 系统研发 + 业务确认 | 一行代表什么、主键、更新时间、数据边界 |
| 字段语义 | 系统研发 + 业务确认 | 含义、单位、空值、时间与敏感级别；结构预填 |
| 关联与映射 | 系统研发/数仓 | 真实关联、基数、去重、字典及术语映射 |
| 字典码值 | 系统研发/业务 | 字典范围、原始码值、含义、有效期 |
| 术语定义 | 业务口径负责人 | 术语、别名、边界、例子及关联对象 |
| 指标口径 | 业务口径负责人 | 定义、粒度、时间、维度、公式、排除、聚合边界 |
| 指标实现 | 数据研发 | 来源、字段表达式、关联、过滤、SQL与测试依据 |
| 模型登记 | 项目组/数仓架构 | 现状或新设计、分层、粒度、主键、历史与清理 |
| 作业与运行 | 研发/调度/运维 | 接入和加工类型、脚本、DAG、实例与处置约束 |
| 质量规则 | 业务 + 研发 | 六类规则、检查范围、阈值依据和修复边界 |
| 知识资料 | 各提供方，项目组整理 | 原件、适用范围、版本、来源和发布引用 |
| 问题与确认 | 项目组协调，责任人答复 | 明确冲突、结论及受影响定义版本 |
| 评测案例 | 业务 + 研发 + 测试 | 真实问句、预期行为、结果依据、数据快照 |
| 平台与资源 | 平台/运维 | 测试连接、工具能力、资源、网络和权限；不填密码 |

全套模板是对象目录，不是要求每个人一次填十五张。首轮只收系统/人员、范围内表字段、字典和关键关系、选中指标、现有SQL与验证样本；模型登记由项目组整理，运维和大规模盘点资料在相应阶段补齐。

模板中的逻辑记录ID只用于收集关联，不改变现有 `table_schema` / `data_asset_code_kb` 字段契约，不假设已有全限定资产ID。项目组应保留“收集ID → 原系统标识/表字段名称/字典名称”的映射，存在跨系统同名时按受控来源范围区分，不能覆盖同名记录。

## 5. 哪些进知识库，哪些保留精确结构

| 内容 | 推荐保存方式 | HiAgent 如何使用 |
|---|---|---|
| 制度、分层/编码规范、解释性案例、故障手册 | 已发布知识文档，附ID、版本、适用范围及来源 | 检索定位、理解和解释；按引用组织回答 |
| 表字段、字典与码值、指标定义及技术映射 | 已有权威库/平台，或经核验的版本化结构记录 | KB定位候选后，结构化工具核验和取精确信息 |
| 术语 | 结构化登记 + 可检索的条目文档 | 支持别名召回；精确定义按有效版本核验 |
| 原始SQL与运行日志 | 代码/日志平台或受控附件 | 按版本和授权范围读取；不把全量日志塞入知识库 |
| 评测答案、盲测SQL与预期结果 | 与运行知识分离的受控测试目录 | 仅评测使用，避免答案泄漏 |

同一条定义可以同时有检索文档和结构记录，但须共享ID、版本与来源。发布流程核对两者一致性；有同步延迟时事实核验仍以权威结构记录为准。知识库更新不等于模型训练，也不需要先微调模型。

### 5.1 在项目中落成哪些治理子模块

这些能力先作为B1下边界清楚的接入、审核和发布组件，不新增一个全能治理服务；有现成平台时适配其能力。HiAgent可以辅助整理和解释，不拥有正式定义的最终确认权。

| 子模块 | 需要实现的操作 | HiAgent与原平台的关系 |
|---|---|---|
| 资料接收与结构导入 | 登记材料批次、原件版本、提供人；映射Excel/CSV/数据库导出；检查必填、类型、ID引用和编码 | 导出能自动取得的结构；模型只对原材料抽取草稿 |
| 待确认区与问题处理 | 保存原值、建议值、依据、冲突和影响对象，按责任人分派 | 复用既有任务/治理平台或B5记录；首期可人工表格跟踪 |
| 定义确认与发布 | 校验确认记录、有效期、适用域和权限，形成不可混用的资料批次 | 正式结构记录由B1读取；H3绑定相应已发布知识资料 |
| 知识转换与索引更新 | 按条目ID/版本生成检索文档，触发平台支持的上传/更新，验证可检索且旧定义不误用 | 平台不提供API则使用受控人工上传清单；未核实前不承诺自动同步 |
| 变更与评测触发 | 跟踪结构/口径/代码版本漂移，标记旧映射或成果失效，重跑相关用例 | 已有采集或变更通知优先；缺接口时按约定周期导出比对 |

最小发布链路：**原始材料 → 待确认记录 → 技术核验与业务确认 → 已发布结构记录及知识条目 → HiAgent检索与B1核验 → 评测反馈**。确认或索引更新不成功时保留上一有效版本或停止受影响查询，不发布一半后把新旧内容混作同一版本。大规模自动化前，先用人工执行同一发布清单验证一批资料。

## 6. 需要什么人、环境和基础设施

### 6.1 首期必须落实的支持

- 客户侧：有权决定试点范围和口径的负责人、业务专家、系统研发联系人、平台/运维及测试支持。业务专家要参加样例确认和错误复盘，不能仅交一份资料后退出。
- 项目侧：业务分析/数据建模、HiAgent配置与评测、后端和平台适配、测试四类职责；可兼任，不把职责数等同固定人数。
- 模型与HiAgent：现有平台可用、模型版本和配置可记录、可看实际知识/工具输入输出、能区分失败与零结果。
- 数据与测试：受控只读元数据、脱敏或合成测试数据、一个明确SQL引擎、业务认可的预期结果、隔离验证环境。只有结构时仍可做查询/草稿MVP，但不能完成业务结果正确性验收。
- 连接和权限：平台到模型、知识库、工具服务与测试引擎的网络连通；按用户/服务身份授予范围；凭据由受控连接管理，不收进Excel。

### 6.2 资源建议及扩容条件

| 资源 | MVP建议 | 何时增加 |
|---|---|---|
| HiAgent服务器 | 优先复用现有部署，向平台方确认租户配额、节点、存储、日志和可用性 | 扩用户、并发和长任务前按厂商部署要求及实测扩容 |
| 大模型/GPU | 复用现有企业模型服务或获准API；调用额度、超时、上下文限制需确认 | 内网限制必须本地推理时，按具体模型、量化、上下文和并发另测；不直接承诺某张GPU够用 |
| Embedding与重排 | 先复用HiAgent已有检索模型；记录版本与知识库更新行为 | 召回评测证明不足且平台允许替换时再优化，不能只改模型而不重建对应向量 |
| 独立向量库 | 首期不新增，先测试已有知识库能否覆盖检索 | 明确需要独立索引控制、权限过滤、增量维护或容量且平台不能满足，并有对照评测时引入 |
| 适配/校验后端 | 如果现有工具不足，开发测试可先用1台4vCPU、8—16GiB内存、约100GiB持久盘的虚机/容器资源作为起测预算 | 这是小规模I/O型服务规划，不含LLM/向量引擎/SQL计算，非容量保证；生产隔离和高可用另配 |
| 元数据/成果存储 | 优先已有数据库、版本库和文件存储；新增记录只存定义、版本和证据引用 | 长任务续接、版本确认和审计需要可靠持久化时补齐；新MySQL库表使用utf8mb4 |
| SQL测试计算 | 复用隔离的目标引擎，不在适配服务虚机上跑大规模ETL | 根据数据量、分区、扫描字节和并发单独测容量 |
| 日志与监控 | 复用现有平台，保留脱敏工具轨迹、耗时、错误与版本 | 请求量增长时按实际日志大小、保留周期和查询需求扩容 |

服务器预算假设：一个业务域、约20张范围内表、5—10名试用者、初始2个并发任务、模型和SQL计算外置。用同一数据和任务逐步测2、5个并发，记录后端CPU/内存、连接占用、模型配额、P50/P95、超时和扫描量，再定资源。压测必须遵守测试环境允许负载，不以并发数字替代容量验证。Embedding存储可按“分片数×向量维度×每维字节”估算原始向量，下加索引、文本、副本与版本开销；不能只凭文档文件大小报价。

## 7. MVP主线：一条可对账的数据研发链路

**推荐主线：资产核验 → 指标口径确认 → 模型/SQL草稿 → 引擎检查和业务对账 → 质量验证。** 同时覆盖客户资产检索、需求理解、建模、编码、质量五类目标的有限范围；调度运维先验证接口可接，不首期承诺生产自动修复。

### 7.1 范围建议

- 一个业务域、一个主要系统；确需跨系统才增加第二个来源。
- 一张已有报表或一组业务认可的指标，先选3个左右：简单汇总、带过滤/去重、带一次关联。具体按数据真实复杂度裁剪。
- 约10—20张相关表、10—30个关键术语，优先补齐相关字段、关联和字典，不做全库治理。
- 一个SQL引擎，一组可复现数据快照；先支持约定范围批处理SQL。Shell或生产调度按后续适配和执行边界单独验收。
- 如果客户没有现成指标，业务方仍须对一个报表问题给出计算规则和小样本预期结果。项目组可以协助整理，不能让模型自产定义再自证正确。

### 7.2 四个验证阶段

| 阶段 | 输入 | 验证什么 | 退出条件 |
|---|---|---|---|
| M0 资料和平台可用 | 原材料、责任人、引擎、实际KB/DB轨迹 | 含歧义的一次KB→DB、真实错误、工具范围、版本读取与必要节点能力 | 目标数据可访问，口径责任明确，资料缺口可追踪；否则缩为查询/设计试点 |
| M1 资产与语义可用 | 已确认术语、表字段、字典、关键关系、指标定义 | 找对候选、识别同名、正确确认、精确码值、缺失不编造 | 资产/口径盲测达标，知识与事实版本可追溯 |
| M2 设计与代码可用 | 确认版需求、规则、事实证据、测试数据 | 粒度和关联合理、SQL可执行、结果符合预期、错误能定位 | 真实需求成果包通过独立业务/研发复核，关键样本对账通过 |
| M3 质量和链路可验证 | 正反样本、规则、测试作业接口 | 六类质量规则的适用范围、异常发现、测试实例状态、失败定位 | MVP必需规则有执行和结果证据；可用时试接一条测试调度，后续再扩自主处置 |

M3不强行凑齐六类“自动修复”。可先对完整性、唯一性等易确定规则验证；准确性需要权威对照，波动性需要基线，时效性需要到达时间/约定SLA。缺少条件的类型标未覆盖；若客户要求六类作为验收项，必须补足对应数据和判据再验收。

## 8. 如何验证：把准确率拆到可定位的阶段

### 8.1 测试资料和方法

建议先准备约30条调试用例，另冻结50条盲测用例，按业务对象/指标族或场景模板分组切分，避免只换词后两边都有同一答案。盲测答案、预期SQL和结果不得上传运行知识库。某些生产事实可被系统正常查询，但测试答案本身应隔离。

盲测50条可先分配：资产/语义20条、设计与SQL20条、控制及失败路径10条。每类含充分资料、歧义和缺失情况，逐项写预期动作、事实引用、确认方式及完成条件。数量是建议，不构成统计充分性保证。每题独立重复3次，分别记录题级通过与运行级波动；不能把150次相关运行当150个独立业务样本。

SQL预期不能只比较字符串。由业务和研发共同核定可接受语义，执行到冻结的测试数据，按键和粒度比较结果；金额等容差由业务确定，不能用统一浮点容差覆盖所有字段。至少加入重复、NULL、日期边界、前导零、状态过滤、退款/撤销、关联一对多和零分母等适用边界；没有相应业务规则的边界要标不适用。

### 8.2 指标及初始验收建议

| 指标 | 分母与判定 | 建议讨论起点 |
|---|---|---|
| 候选召回Recall@5 | 有已知相关资产的检索请求中，正确目标进入前5候选的数量/应召回目标数量；多目标逐目标计，越权候选不算命中 | ≥95%，固定k并报告实际分子/分母 |
| 精确事实正确率 | 最终展示的可核验事实断言正确数/已展示可核验事实断言数；同时记录应答覆盖，避免少答抬分 | ≥98%，错误标识/码值等关键错误单列 |
| 歧义与缺失处理正确率 | 应澄清或应停止的案例中，实际动作、候选与边界符合预期的案例数/此类案例总数 | ≥95%；错把未知标已确认列关键失败 |
| SQL执行通过率 | 工具及测试条件已提供、预期应生成SQL的案例中，生成后能在目标引擎执行的案例数/此类案例数；生成失败计失败 | ≥90%，不能以执行成功代替口径正确 |
| 可回答任务端到端成功率 | 资料充分且可完成的请求中，正确事实、设计/SQL、结果与必要验证均达标的案例数/此类请求总数；拒答和只给部分仍计未完成 | 初始≥85%，据难度和基线协商，不宣称当前已达到 |
| 质量规则检出与误报 | 分别在已标注异常样本和正常样本上统计检出、漏报、误报；按规则类型分层 | 对MVP约定规则给具体样本判据，不拿生成规则数量验收 |
| 时延、成本与人工修改量 | 同模型/配置/数据/任务比较P50、P95、调用次数、可得费用及人工修改用时 | 先量基线，再定预算；费用未知不估算 |

关键失败必须单列且不被平均分抵消：越权、未经授权执行、虚构资产、把未执行/失败标为验证通过、把待确认口径标已确认。验收样本出现任一项即暂停扩大范围并修复；样本内0次不代表生产绝对不会发生。

同时报告：总任务成功率、资料充分任务成功率、澄清/拒答正确率和实际覆盖率。测试环境不可用不计为模型错误，但要记工程阻塞和本轮覆盖缺失，不能在端到端报告中当成功或静默剔除。

## 9. 架构如何提高有效性

架构可以约束路径、提供证据和阻断部分错误，不能仅凭图纸保证答案正确。

| 执行环节 | HiAgent职责 | 确定性边界及证据 |
|---|---|---|
| 需求抽取 | 生成结构化草稿和待澄清项 | 检查输出字段；未确认的时间、口径、粒度不变成既定事实 |
| 候选检索 | 在授权已发布范围内发现候选 | 状态/权限过滤须由平台或独立资料集实现；无召回有界结束 |
| 精准核验 | 按现有KB→DB原则使用事实工具 | B1/现有DB返回真实标识、原始码值、范围和版本；不以检索片段替代核验 |
| 口径确认 | 展示缺口和差异，引导责任人确认 | B5/既有记录保留确认人、版本与证据；模型自报confirmed不生效 |
| 方案与代码生成 | 从确认版输入生成草稿 | 工具校验资产引用和适用规则；未知映射不得填入确定码值 |
| 验证 | 调用B2/B3、解释工具结果 | 语法/编译、引擎试跑、独立结果对账；模型自评仅为辅助 |
| 交付或执行 | 提交具体成果版本 | 原发布流程或可信授权检查；需求/SQL内容变化使旧验证和授权失效 |
| 运行与反馈 | 根据真实实例和日志诊断 | 原平台执行和留存状态；修复必须复验；失败与部分保留原貌 |

平台具备可执行规则/条件节点时优先复用。没有时，后端工具入口仍需校验本操作前置条件；不能只在SKILL里写“必须”就宣称工程上已阻断。只允许NL2SQL时要检查实际SQL或执行条件，无法观察则保留相应核验限制。

## 10. 准确率提升的实际顺序

1. **补关键事实**：优先修正错误字典映射、粒度、日期含义和过滤条件。没有依据的问题先治理，不靠提示词补猜。
2. **修召回**：按错误类别补同义词、适用域和结构清晰的知识条目，保证定义、范围、例子、版本不被切散；用命中测试观察。对原HiAgent KB入口保持既定顺序。
3. **修精确查询**：使用稳定标识、配对条件、原始字符串、统计与真实分页；消除同名跨对象误用。优先参数化/固定查询形状，平台不支持则明确NL2SQL边界。
4. **修生成输入**：按场景给确认版任务、相关证据和适用规则，减少无关材料；SKILL定义任务完成条件和停止边界，不逐条硬编码业务问句。
5. **加独立验证**：SQL执行后用有边界样本和权威结果对账；设计与代码评审不以同模型同上下文的赞同作为正确性证据。
6. **再比较检索/模型方案**：同一冻结集，一次改变一个因素；只在效果不足的环节引入重排、独立检索或更强模型，记录成本。微调后置，需足够高质量标注且证明提示/检索/工具已不能覆盖。
7. **回归与发布**：每次错误按资料、召回、映射、生成、工具、展示、平台状态归因；记录taskId、模型/模式/SKILL/知识/工具版本和阶段耗时。新样本加入调试集，保留未污染验收集，变更触发受影响回归。

## 11. 项目启动时要落实的决策

先锁定业务域与报表/指标场景，再落实业务口径裁决人、系统研发、平台联系人和测试负责人；明确能否查询真实或脱敏样本、目标SQL引擎、现有报表/SQL/预期结果；给出HiAgent工具与流程能力的实际证据。无需先决定采购独立向量库或GPU。

第一批交付应是：场景确认单、预填模板与缺口单、已确认资料版本包、一条可追踪的HiAgent工具链、可复现测试数据和评测报告。资料、工程和测试一起验收，才能判断客户目标中哪些能力已实际落地。
