## 03 · 过去，如何判断一个工程师靠不靠谱？

章节：一 · 版式：S04

位置：程序员的价值 → 1.1 工作与角色变化

### 投屏要点

- **交付**：说好的范围 / 时间
- **质量**：故障 / 缺陷 / 可维护性
- **解题**：解决过什么难题
- **业务**：效果能否解释清楚
- **协作**：依赖能否推进
- **成长**：新问题能否接住

### 展开内容

- **交付表现**：是否在约定范围与时间内交付，兑现承诺；不是单看工作量。
- **工程质量**：实现是否正确、稳定、可维护，是否控制故障和技术债。
- **技术解题**：能否解决与岗位相关的复杂问题，诊断故障并选择合理技术方案。
- **业务贡献**：是否改善用户效果、业务收益或团队效率；不同岗位的贡献距离不同。
- **协作推进**：沟通、主动补位、协调资源和推动问题闭环是否有效。
- **成长与投入**：学习能否迁移到工作，持续改进并承担职责；主动性、抗压是支撑这些结果的能力。
- **本页的具体讲法**：交付：说好的范围 / 时间；质量：故障 / 缺陷 / 可维护性；解题：解决过什么难题；业务：效果能否解释清楚；协作：依赖能否推进；成长：新问题能否接住

主讲备注：这是常见的工作评价维度，不宣称所有公司使用统一体系。岗位、级别、团队和阶段会改变权重。先从“做出了什么结果、以什么质量交付、如何解决问题并推进工作”解释过去的价值，再讨论 AI 的影响。技术能力、主动性、学习、抗压等是支撑这些结果的能力，不能与评价结果混为一层。参考 Monzo、CircleCI 的公开职业发展框架，但本页六个维度是分享用的归纳，不是照搬某一家公司的评分表。

收束：岗位、级别与团队阶段不同，权重不同；能力最终要体现为工作结果。

## 05 · 同样一张工单，差距会出在哪里？

章节：一 · 版式：S08

位置：程序员的价值 → 1.1 工作与角色变化

### 投屏要点

- **只完成局部实现**：按描述生成代码
跑通正常路径
把未知留给下游
- **把问题往前推进**：追问重复和失败语义
比较复用与自研成本
补齐异常用例和验收

### 展开内容

- **单独依赖它，更难形成优势**：记住用法 → 随时可查；常规实现 → 更易获得；产出数量 → 不能证明效果
- **同样能力，可以创造更多价值**：主动发现问题 → 更快验证机会；业务与技术判断 → 指导更多执行；学习、协作、抗压 → 驾驭变化与风险
- **本页的具体讲法**：只完成局部实现：按描述生成代码 / 跑通正常路径 / 把未知留给下游；把问题往前推进：追问重复和失败语义 / 比较复用与自研成本 / 补齐异常用例和验收

主讲备注：降低的是常规执行和知识获取的稀缺性，不是软件工程的整体价值。工程质量、复杂解题和交付结果仍然重要。AI 扩大主动性、业务判断、学习与协作的作用范围，但效果必须通过实际工作证明。这里是对价值变化的分析，不是所有公司的新考核标准。

收束：执行更容易获得；质量、复杂解题、业务效果与责任仍然重要。

## 06 · 借鉴 FDE：从需求跟到实际效果

章节：一 · 版式：S19

### 投屏要点

- **问清现场**：谁在用 / 哪里卡住
- **作出取舍**：范围 / 成本 / 风险
- **贯通交付**：前后端 / 数据 / 测试
- **跟踪效果**：采用情况 / 运行问题

### 展开内容

- **业务贴近**：确认真实问题、用户操作与约束。
- **技术贯通**：理解需求、设计、前后端、数据、测试及上线之间的联系。
- **结果负责**：衡量上线采用、业务效果、运行质量；推动问题解决。
- **保留专长**：扩大责任范围，持续打磨一个可以解决难题的专业深度。
- **本页的具体讲法**：问清现场：谁在用 / 哪里卡住；作出取舍：范围 / 成本 / 风险；贯通交付：前后端 / 数据 / 测试；跟踪效果：采用情况 / 运行问题

主讲备注：FDE（Forward Deployed Engineer，前沿部署工程师）可以作为参照：贴近客户和业务现场，完成问题发现、范围界定、系统设计、开发、上线，并衡量实际使用效果。OpenAI 公开岗位明确包含全栈系统、客户协作、质量与进度取舍、生产部署和评估反馈。FDE 不是所有程序员的统一职业终点，也不等于一个人精通全部技术或包办产品、研发、测试。更实用的定位是：保留一项深度，能理解上下游，用 AI 和团队贯通交付；关键环节能判断、能验收，遇到专业难题知道何时请专家。前端和后端专家需要警惕的是只接受局部工单、不了解业务与结果；深度性能、可靠性、安全、基础设施等专业能力仍有独立价值。

## 08 · 两种能力，用两个任务区分

章节：一 · 版式：S08

位置：程序员的价值 → 1.2 两条 AI 能力路线

### 投屏要点

- **用 AI 完成工作**：分析一次同步故障
输出原因与修复建议
你来核验和决定
- **把 AI 做进产品**：让用户自助诊断故障
接入数据与诊断工具
系统控制权限和失败

### 展开内容

- **使用 AI：提高个人效能**：辅助工作与学习
编码、研究、文档、理解
会提问、给上下文、验收
- **嵌入 AI：交付项目与产品**：将 AI 接入真实业务
模型、知识、工具、流程
做到可靠、安全、可运营
- **工程基础**：系统、数据、接口、安全
质量、部署与维护
- **AI 增量**：个人提效与模型接入
知识、智能体与评估
- **业务结果**：更好的效果与体验
可控成本与持续运营
- **本页的具体讲法**：用 AI 完成工作：分析一次同步故障 / 输出原因与修复建议 / 你来核验和决定；把 AI 做进产品：让用户自助诊断故障 / 接入数据与诊断工具 / 系统控制权限和失败

主讲备注：第一类是使用 AI 完成日常工作和学习：描述问题、组织上下文、调用工具、审查结果，并借助反馈建立理解。第二类是将 AI 能力嵌入项目与产品：判断 AI 是否适用，设计数据、模型、工具和业务流程，评估质量，处理权限与失败，上线并持续运营。两类能力可以互相促进，但会使用聊天或编码工具并不自动具备完整产品落地能力。
用户提出的时代视角可以表述为：软件工作的价值重心正在向具有 AI 能力的软件和产品扩展。这是本次分享的判断，不是所有软件需求都必须引入 AI，也不是传统工程能力自动失效。相反，系统设计、数据质量、安全、测试和运维是 AI 产品可靠落地的基础。在这些基础上增加模型、知识、智能体与评估能力，再用业务效果衡量是否真正增值。

收束：一条线提高自己的工作能力；另一条线为项目和产品创造新能力。

## 09 · 把一次排障，变成下一次的能力

章节：一 · 版式：S05

位置：程序员的价值 → 1.2 两条 AI 能力路线

### 投屏要点

- **一次问答**：给日志 → 问原因
- **固定流程**：给规范 → 查链路 → 验证
- **经验复用**：反例 + 脚本 → 排障 SKILL

### 展开内容

- **会问**：能提出问题、给上下文、辨别答案，完成工作与学习中的单次任务。
- **会用**：能复用规范、SKILL 与工具流程，定义验收标准，并稳定完成一类任务。
- **会沉淀**：能将自己的知识、方法与反例变成可复用资产，交给 AI 执行并持续维护。
- **如何验证**：同类任务的质量更稳定、人工介入更少，经验能够被他人复用。
- **本页的具体讲法**：一次问答：给日志 → 问原因；固定流程：给规范 → 查链路 → 验证；经验复用：反例 + 脚本 → 排障 SKILL

主讲备注：这是为交流提出的三个能力阶段，不是行业认证等级，也不按使用哪款产品划分。豆包等聊天或智能体产品可以承载多种使用方式，聊天也可处理有上下文的专业任务。第一阶段，临时问答、解释概念、生成初稿；需要提供必要上下文并核查重要结论。第二阶段，给出项目规范、材料和验收标准，组合现成 SKILL，把任务组织成可重复的流程；判断标准是结果是否稳定，而不是装了多少插件。第三阶段，把自己的业务知识、判断规则、案例、失败经验整理成文档、检索知识库、自建 SKILL 和脚本，将重复工作交给 AI，并持续维护和检验这些资产。这里的“蒸馏自己的能力”是经验显性化与流程沉淀的比喻。模型知识蒸馏是另一种训练技术，不应混用。检验是否真正进步：同类任务是否少重复解释、少人工纠错，换个人能否复用；敏感材料只进入已获授权的工具和环境。

## 10 · 诊断助手：怎样从 Demo 走到上线？

章节：一 · 版式：S05

位置：程序员的价值 → 1.2 两条 AI 能力路线

### 投屏要点

- **先跑通**：读日志 / 找原因 / 给建议
- **再控质量**：已知故障集 / 权限 / 拒答
- **持续改进**：新故障入库 / 回归 / 灰度

### 展开内容

- **功能可用**：围绕真实业务任务打通输入、处理、输出；最小验收与权限边界从第一版存在。
- **质量可控**：有代表性评估数据、明确判定标准、可观测运行与失败处理，能够量化质量和成本。
- **持续改进**：基于实际反馈提出改动，通过独立评测和回归决定发布，保留版本、审计与回滚。
- **模型与接口**：能力边界、API、结构化输出
- **上下文与知识**：检索、Memory、业务语义
- **智能体与工具**：任务编排、MCP、执行反馈
- **评估与验证**：评估集、效果、失败与回归
- **安全与权限**：数据边界、工具权限、人工介入
- **运行与迭代**：成本、延迟、日志、监控、恢复
- **本页的具体讲法**：先跑通：读日志 / 找原因 / 给建议；再控质量：已知故障集 / 权限 / 拒答；持续改进：新故障入库 / 回归 / 灰度

主讲备注：产品路线也分三个阶段，但从第一版就要有最小验收用例，涉及数据和动作就要定义权限。功能可用：用最简单方案跑通有价值的任务；按需求选模型、检索、SKILL、MCP，不要求全部接入。组件数量不是成熟度。质量可控：建设代表性评估集，覆盖正常、边界、失败和越权场景；建立工具契约、运行观测、成本与延迟指标、人工接管与恢复。持续改进：将真实失败转成可复现案例，用评估对比提示词、检索、工具、工作流或模型的新版本，确认效果后灰度发布，可回滚。智能体可辅助提出和实现改进，但“自己说更好”不构成升级依据；自我修改也不是自动训练了模型。复杂业务需要时，再引入领域语义模型或本体；训练、微调、多智能体也由实际缺口决定，而非升级必经步骤。
学习知识要与真实项目结合。先理解模型边界与接口，再决定需要哪些知识、工具与流程；建立评估集验证效果；用权限边界、失败处理、日志和监控保证可运营。SKILL、Memory、MCP、本体等各有职责，后面方案章节会进一步解释。训练或微调是在明确持续问题和数据条件后考虑的能力，不是所有产品落地的必选项。

## 11 · 助手答错了，下一版怎么改？

章节：一 · 版式：S11

位置：程序员的价值 → 1.2 两条 AI 能力路线

### 投屏要点

- **收集失败**：保存输入和预期
- **定位原因**：知识 / 检索 / 工具
- **比较版本**：留出集 + 回归
- **发布观察**：监控 + 回退

### 展开内容

- **收集失败**：真实案例
- **提出改动**：先在隔离环境

## 17 · 候选方案表，要查到这些依据

章节：二 · 版式：S04

位置：需求与设计 → 2.1 需求澄清与调研

### 投屏要点

- **能力匹配**：恢复 / 幂等：是否支持
- **维护情况**：版本 / Issue / 提交
- **接入条件**：许可 / 部署 / 依赖
- **改造位置**：扩展接口 / 事务边界
- **关键源码**：提交与检查点的先后
- **验证实验**：提交成功后，模拟断网

### 展开内容

- **候选来源**：GitHub、Gitee、官方文档，以及项目已经引入的组件。同时寻找最匹配和高关注度方案。
- **匹配程度**：必须需求是否正式支持？哪些需要改造？不要只看 README 中相似的关键词。
- **关注与维护**：记录星数、查询日期、版本、近期维护、issue 响应。星数用于发现候选，不能证明适配或质量。
- **使用条件**：许可证、技术栈、数据库、部署方式、依赖、资源和数据处理条件。
- **成本与风险**：二次开发、运维、升级、迁移、退出成本，以及已知缺陷和边界。
- **调研交付**：候选对比表 + 来源链接 + 适配理由 + 未验证项。搜索不可用时，明确说明信息缺口。
- **读文档与问题**：核查能力、限制、版本、部署和已知问题。
同步案例：哪些数据源？全量与增量如何工作？
- **读关键源码**：定位扩展点、重试、状态、事务和恢复路径。
核查文档承诺在目标版本如何实现。
- **做最小验证**：最高风险假设先实验，再投入详细设计。
例如：响应超时后的重复请求是否幂等？
- **本页的具体讲法**：能力匹配：恢复 / 幂等：是否支持；维护情况：版本 / Issue / 提交；接入条件：许可 / 部署 / 依赖；改造位置：扩展接口 / 事务边界；关键源码：提交与检查点的先后；验证实验：提交成功后，模拟断网

主讲备注：不要让 AI 用模型记忆代替当前互联网检索。要求访问官方项目与版本文档，重要结论指出来源位置；跨平台星数不能直接视为相同评分。
研究不等于读完整仓库。先列影响选择的问题，再限定需要阅读与验证的路径。交付结论包括证据、失败结果、限制以及为何保留候选。
调研动作：先检查仓库已有模块，再检索 GitHub、Gitee 和官方资料；选 3–5 个候选，记录链接、版本、检索日期。星数仅作受关注程度参考，按匹配度、维护、许可和改造成本筛选。最高风险假设用小实验核验，不把 README 承诺当成已验证能力。

收束：先缩小候选范围，再选一个或几个深入研究；不能因为星最多就直接定方案。

## 18 · Grill me：让 AI 问到你能拍板

章节：二 · 版式：S04

位置：需求与设计 → 2.1 需求澄清与调研

- **覆盖与调整**：对照需求：直接复用什么？放弃什么？适配什么？新增什么？
组合多个方案时，接口与运维边界怎样衔接？
- **复杂度与成本**：实现复杂度、改造 / 创建、迁移、测试、运维、升级成本。
估算标明前提，不把 AI 的估计当项目承诺。
- **风险与限制**：哪些依赖最脆弱？哪些约束无法保证？
失败影响、规避措施、验证方式与残余风险。
- **效果与选择**：完成后达到什么效果？怎样证明？
为什么选它？哪些条件变化后需要重新选择？
- **本页的具体讲法**：先列约束：同步恢复 / 不重复 / 接入现有架构 / 开发与运维预算；逐项比较：复用：现有能力差什么？ / 改造：改哪里、升级多难？ / 自研：为什么已有方案不够？

| 路径 | 要验证什么 | 代价与退出 |
| --- | --- | --- |
| 复用现有 | 恢复与去重是否已具备 | 补缺口 / 保持现有运维 |
| 改造成熟方案 | 扩展点与事务能否适配 | 接入 / 升级 / 迁移成本 |
| 必要时自研 | 已有方案缺口是否不可补 | 自担测试、恢复与运维 |

主讲备注：这张表展示交付格式和比较逻辑，并没有替任何具体候选完成选型。真实表格还可加入许可证、活跃度、部署条件和效果指标；来源和验证结果要与结论关联。
要求 AI 输出多方案对比表，同一组需求和约束作评价依据。至少保留复用现有能力、成熟方案适配、必要自研这几个路径；不是必须每个都开发。
这张表是比较模板，不是某个开源产品的实测结论。请 AI 代入已检索候选的目标版本与来源；“自研最灵活”不能代替维护成本分析。

收束：让 AI 填表只是开始；逐项追问证据，才完成方案选择。

## 23 · 一个验收例子：重试不重复

章节：二 · 版式：S19

位置：需求与设计 → 2.3 阶段任务与验收

### 投屏要点

- **先写入**：数据库已成功
- **制造故障**：响应丢失
- **再次请求**：同一业务标识
- **检查结果**：一条记录 / 状态正确

### 展开内容

- **目标与前提**：目标：重复请求不重复产生业务记录。
前提：已确认任务标识、数据版本和重试语义。
本阶段不做完整管理页面。
- **实现与交付**：在选定方案上跑通单个任务写入和重复提交。
交付实验代码、配置、执行步骤和结果记录。
- **验收动作**：首次写入成功后模拟确认响应丢失，再重试。
查询业务记录与任务状态；检查错误与恢复日志。
- **通过与退出**：符合约定的不重复写入、合法状态和可恢复行为。
不能满足就记录证据、调整方案，不直接进入下一阶段。
- **输入与前置条件**：需求与设计版本、依赖任务、测试数据、环境。
未满足前置条件，不应自行猜测继续执行。
- **交付物与范围**：具体功能、接口、文档、实验和数据。
明确允许修改的位置与本阶段不做的内容。
- **验收与证据**：执行步骤、预期结果、测试、日志与实际结果。
能让另一个人重新执行并判断。
- **通过与回退**：哪些问题阻塞？谁确认？失败怎么处理？
未验证项、残余风险和进入下一阶段条件。

主讲备注：这是教学任务卡。具体标识、状态和数据语义要由项目需求决定，不能当作默认协议。通过标准应能让另一个人重复执行，而不是“AI 说已经幂等”。
示例：幂等实验阶段交付提交成功但响应丢失的重试测试；最小闭环交付一张表从配置到同步完成的可运行路径。不能用“完成开发”作为唯一通过条件。

收束：任务卡写到“如何判断通过”，才真正可以交给智能体执行。

## 29 · 缺什么，再补哪种 AI 能力

章节：二 · 版式：S04

位置：需求与设计 → 2.5 SKILL 与知识工具

### 投屏要点

- **步骤总漏**：SKILL：固定步骤与验收
- **偏好总忘**：Memory：稳定规则与背景
- **工具不通**：MCP：连接工具与数据
- **事实过期**：RAG：检索当前有效资料
- **行为不稳定**：微调：有数据后再评估
- **术语不一致**：本体：对象、关系、约束

### 展开内容

- **SKILL：怎么做**：复用步骤、模板、脚本与验证方法。要看触发、输入输出、失败处理，避免多个工作流冲突。
- **Memory：长期知道什么**：记录稳定偏好、规则、术语与已核验事实。要有来源、更新和清理，避免旧记忆覆盖新需求。
- **MCP：能接什么**：提供连接工具和数据的标准协议。工具权限、可靠性和结果核验仍需另外设计。
- **检索 / RAG：本次需要什么**：按任务取得资料与事实。要核对版本、时效与来源，检索到不等于证实。
- **训练 / 微调：改变模型行为**：通过训练数据调整能力和行为，不等于记住对话。先排查上下文和工具问题，再评估投入。
- **本体 / Ontology：业务如何定义**：明确对象、关系、属性、规则与动作，形成共享业务语义。可先从领域模型和术语开始。
- **本页的具体讲法**：步骤总漏：SKILL：固定步骤与验收；偏好总忘：Memory：稳定规则与背景；工具不通：MCP：连接工具与数据；事实过期：RAG：检索当前有效资料；行为不稳定：微调：有数据后再评估；术语不一致：本体：对象、关系、约束

主讲备注：这些概念不能互相替代。缺实时知识优先检索，缺工具接入检查协议，缺过程纪律考虑 SKILL，持续行为问题再考虑训练。这里本体模式按 Ontology 理解。

收束：技术选择也遵循需求：先确定缺口，再选择机制；不要为了技术名词增加系统复杂度。

## 30 · “测试全绿”，为什么仍然不能直接收？

章节：三 · 版式：S08

位置：Review 与放行 → 3.1 审查依据与标准

### 投屏要点

- **可能漏掉什么**：需求理解错了
测试跟着实现一起错
只覆盖正常路径
- **再拿业务反例来验**：写入成功但响应丢失
没有权限的人发起重试
旧版本请求再次提交

### 展开内容

- **常见的失控路径**：AI 连续生成大改动 → 人只看总结 → 测试全绿就接受。
需求、设计和实现逐渐脱节。
最后代码越来越多，项目 / 产品的把控能力越来越弱。
- **应当建立的控制方式**：严格确认需求和设计，开发按阶段推进。
AI 按需求、设计与工程规范独立验收。
人阅读关键路径、核查证据，确认自己能维护后放行。
- **本页的具体讲法**：可能漏掉什么：需求理解错了 / 测试跟着实现一起错 / 只覆盖正常路径；再拿业务反例来验：写入成功但响应丢失 / 没有权限的人发起重试 / 旧版本请求再次提交

主讲备注：这章不只是“如何找 bug”，还要讨论如何保持项目理解。需求、设计文档是验收输入，而不只是前期存档。AI 可以承担审查工作，人不能放弃关键判断。

收束：AI review 可以减少审查负担，但不能成为不理解代码的理由。

## 31 · 独立审查者，需要这四份材料

章节：三 · 版式：S19

位置：Review 与放行 → 3.1 审查依据与标准

### 投屏要点

- **需求版本**：已确认规则 + 验收场景
- **设计版本**：时序 / 状态 / 接口契约
- **固定差异**：基线 + 改动 + 关联调用链
- **项目标准**：规范 + 测试结果 + 未验证项

### 展开内容

- **确认的需求**：目标、场景、规则、边界、非目标、验收用例。需求有版本，变更获得确认。

- **质量标准与证据**：工程规范、测试结果、运行日志、场景记录。报告实际执行和未验证项。

主讲备注：提示词示例：分别检查规格符合性和工程质量。每项发现给触发条件、位置、影响和证据；缺事实就列待核验，不用泛泛建议替代缺陷。审查期间固定版本。

收束：需求 → 设计 → 实现位置 → 测试 / 验收证据，建立可追溯关系。

## 32 · 把“质量好”变成具体审查问题

章节：三 · 版式：S04

位置：Review 与放行 → 3.1 审查依据与标准

### 投屏要点

- **正确性**：重试后数据与状态一致？
- **安全性**：能否重试别人的任务？
- **鲁棒性**：并发重试 / 重启会怎样？
- **可维护性**：恢复逻辑是否散落多处？
- **可理解性**：注释讲清意图，日志可定位？
- **可交付性**：兼容旧请求，有回滚路径？

### 展开内容

- **业务正确性**：需求覆盖、规则、状态、不变量、边界；检查遗漏、误解与范围扩大。
- **安全性**：认证授权、输入校验、敏感数据、注入、依赖与工具权限；不能只看是否能运行。
- **鲁棒性**：超时、重试、并发、幂等、部分失败、补偿与恢复；重点走失败路径。
- **可维护性**：单一职责、依赖方向、重复实现、复杂度、复用与工程约束。
- **注释与可观测性**：接口契约、字段与空值语义、关键意图、流程注释；日志能定位路径、分支和异常。
- **性能与交付**：真实规模、资源使用、兼容、数据迁移、部署、回滚，以及分层测试。
- **本页的具体讲法**：正确性：重试后数据与状态一致？；安全性：能否重试别人的任务？；鲁棒性：并发重试 / 重启会怎样？；可维护性：恢复逻辑是否散落多处？；可理解性：注释讲清意图，日志可定位？；可交付性：兼容旧请求，有回滚路径？

主讲备注：质量标准前置到设计。不同模块有不同风险权重；安全、数据一致性等关键问题必要时做专项人工或工具验证。不要把一串质量名词当作已经验收。

收束：每项标准都要对应具体检查或测试方法，结论附证据与边界。

## 33 · 面向对象原则，看它能不能应对变化

章节：三 · 版式：S04

位置：Review 与放行 → 3.2 设计原则与测试

### 投屏要点

- **单一职责**：改一件事，动几处
- **开闭原则**：扩展是否牵一发动全身
- **里式替换**：换实现，行为变不变
- **接口隔离**：是否被迫依赖无关能力
- **依赖倒置**：业务是否绑死实现
- **迪米特原则**：是否越过模块边界

### 展开内容

- **单一职责**：一个类主要因什么变化？是否混入规则、编排、协议、持久化和展示？
- **开闭原则**：已有稳定扩展点能否承担新变化？有没有为了假想未来增加抽象？
- **里式替换**：替换实现后，输入、输出、异常和不变量是否仍满足原契约？
- **接口隔离**：调用方是否被迫依赖无关方法？接口职责和“不负责什么”是否清楚？
- **依赖倒置**：业务是否依赖外部细节？模块边界能否隔离数据库、协议和模型提供方？
- **迪米特原则**：是否穿透多层对象访问内部状态？能否通过恰当的职责接口完成？

主讲备注：审查原则的目的在于读得懂、改得动、边界稳。不能为了符合原则增加单实现接口、工厂或 Context。结合具体变化场景判断，避免形式化打勾。

收束：满足原则靠职责与契约，不靠类和接口的数量。

## 34 · 同一个重试场景，三层测试怎么分？

章节：三 · 版式：S05

位置：Review 与放行 → 3.2 设计原则与测试

### 投屏要点

- **单元测试**：合法迁移 / 重复请求规则
- **集成测试**：真实数据库提交 + 响应丢失
- **E2E**：用户发起 → 失败 → 重试成功

### 展开内容

- **单元测试**：验证规则、边界、状态和关键分支。
案例：同一任务重复提交，幂等规则和合法状态保持正确。
- **集成测试**：验证数据库、事务、协议、依赖与失败交互。
案例：提交已成功但响应超时，重试后不产生重复业务记录。
- **E2E 测试**：验证关键用户操作与完整业务链路。
案例：配置 → 同步 → 查看结果 → 授权重试 → 恢复与审计。
- **本页的具体讲法**：单元测试：合法迁移 / 重复请求规则；集成测试：真实数据库提交 + 响应丢失；E2E：用户发起 → 失败 → 重试成功

主讲备注：TDD 需要看到测试先因目标错误失败，再因修复通过。测试从需求派生，不只复刻实现。按风险定义各层覆盖；测试通过还要记录环境、版本与未覆盖场景。

收束：测试全绿不等于需求正确；覆盖率高也不等于覆盖了关键失败。

## 35 · SDD、TDD、Review，各检查哪层？

章节：三 · 版式：S13

位置：Review 与放行 → 3.2 设计原则与测试

### 投屏要点

- **SDD**：重复请求规则写清楚
- **TDD**：先写超时重试失败用例
- **Review**：规则和测试是否一起想错？

### 展开内容

- **规格驱动 SDD**：明确“应该做什么”，保持需求、设计、任务和实现可追溯。
缺口：规格本身可能错误或遗漏。
- **测试驱动 TDD**：用失败测试约束行为，及时获得实现反馈。
缺口：AI 编写的测试可能固化同一个需求误解。
- **独立 review**：换独立上下文检查规格和质量，追查影响范围与高风险路径。
缺口：也可能漏判、误判；仍要运行验证。
- **Matt Pocock code-review**：规格与规范双轴、独立审查上下文。
优势：不让“代码漂亮”掩盖“做错需求”。
边界：需要明确基线、规格和项目标准。
- **Superpowers**：阶段 review、TDD、完成前验证。
优势：质量反馈融入执行过程。
边界：流程必须实际执行，业务验收仍需补齐。
- **工具内置 review**：例如 Cursor Agent Review 检查本地改动。
优势：接近开发环境，容易运行。
边界：工具检查不能自动覆盖所有业务与安全风险。
- **本页的具体讲法**：SDD：重复请求规则写清楚；TDD：先写超时重试失败用例；Review：规则和测试是否一起想错？

主讲备注：它们是组合关系，不是选一个取代其他。SDD 在此指 Spec-Driven Development；Superpowers 的 subagent-driven-development 是子智能体驱动开发，避免混淆。
使用时明确任务范围与标准。独立模型可以提供不同视角，但不能保证独立错误。静态分析、扫描和测试工具负责能确定验证的部分，不让模型猜执行结果。

收束：需求 / 设计控制方向，测试建立反馈，独立审查找遗漏，场景验收验证结果。

资料：
- https://github.com/obra/superpowers
- https://github.com/github/spec-kit
- https://github.com/mattpocock/skills
- https://cursor.com/docs/agent/agent-review

## 36 · 开独立会话：先找问题，再修复

章节：三 · 版式：S11

位置：Review 与放行 → 3.3 独立审查与放行

### 投屏要点

- **提供基线**：需求 / 设计 / 差异
- **分轴审查**：规格符合 / 工程规范
- **复现报告**：条件 / 位置 / 影响
- **修复复验**：补回归 + 查相邻路径

### 展开内容

- **审查任务**：基于已确认需求、设计、项目规范和固定差异，分别检查规格符合性与工程质量。
读取相关调用链，重点看安全、异常、重试、并发和数据一致性。
不要修改代码；核验不了的内容明确写未验证。
- **报告格式**：每项问题包含：触发场景、代码位置、业务影响、证据、建议验证。
区分确认缺陷、待确认问题和改进建议。
最后列实际运行的检查、未覆盖场景、阻塞项及复验要求。
- **固定输入**：需求、设计、规范、版本与改动
- **独立检查**：规格、工程质量、专项风险
- **核验发现**：复现缺陷；区分疑问与建议
- **修复与测试**：处理根因，验证相关调用方
- **复验放行**：更新证据，明确残余与未验证
- **本页的具体讲法**：提供基线：需求 / 设计 / 差异；分轴审查：规格符合 / 工程规范；复现报告：条件 / 位置 / 影响；修复复验：补回归 + 查相邻路径

主讲备注：适合由独立会话执行，结合 code-review 等 SKILL。固定基线是审查输入；实现者修复后更新版本，再给审查者重新核验。不能只要求“检查安全性”却不给权限与业务规则。
不要把审查输出全部当成真实缺陷。逐个核验触发条件，避免误报驱动无关重构。修复一个共享函数时检查所有调用方；对新改动重新审查必要范围。
可复制给审查者：读取需求、设计、规范及固定差异。只审查，不改代码。沿调用链检查重复请求、提交后超时、并发重试与权限。每项报告触发条件、代码位置、影响、依据和复验步骤；区分确认缺陷、疑问、建议，列出实际执行和未验证项。

收束：验收结论必须附可复验依据；“整体合理、建议加强测试”不构成放行证据。

- https://github.com/obra/superpowers

## 37 · 放行前，自己过这四关

章节：三 · 版式：S19

位置：Review 与放行 → 3.3 独立审查与放行

### 投屏要点

- **解释**：画出写入与检查点链路
- **预测**：说出超时后的状态
- **定位**：从日志找到失败批次
- **修改**：改重试规则并补测试

### 展开内容

- **能解释**：不依赖 AI 总结，讲清入口、调用链、数据流、状态及设计取舍。
为什么放在这里？依赖谁？
- **能推演**：预测正常、失败、边界和并发行为。
响应丢失后重试，会发生什么？
- **能定位**：面对一次故障，知道看什么日志、状态、数据和外部依赖。
能缩小问题范围，而不是连续猜改。
- **能修改**：修改一个关键规则，知道影响位置、调用方及需要补的测试。
不要求背代码，要求可维护关键路径。
- **方向已经确认**：需求与设计基线明确；实现对应需求；范围变化有人确认。
- **质量有证据**：注释、规范、审查、分层测试和关键场景达到预定标准。
- **风险已处理**：重大缺陷闭环；残余风险、未验证项、回滚和负责人清楚。
- **关键路径可维护**：能解释、推演、定位和修改；团队有人负责持续维护与运行。
- **本页的具体讲法**：解释：画出写入与检查点链路；预测：说出超时后的状态；定位：从日志找到失败批次；修改：改重试规则并补测试

主讲备注：现场方法：反向复述一个模块 → 注入超时或错误 → 提出一个小规则变更。通过预测、调试与修改验证理解。不会就缩小改动或补学习和证据，而不是直接合并。
这不是证明绝无 bug，而是在明确约束和证据下作出可负责的交付决策。高风险项目需对应更严格门槛。把结论、版本、证据与限制一并记录。
放行还需实际审查与测试证据、阻塞问题闭环及回退方案；这四关用于检查负责人理解，不能替代质量检查。

收束：“我看过了”不是掌握；能预测并验证，才能维护。

## 39 · 海外工具：每个候选拿一道题试

章节：四 · 版式：S19

位置：工具与模型选型 → 4.1 工具与模型的区别

### 投屏要点

- **Codex**：仓库修复：能否找到关联路径
- **Cursor**：交互修改：人工审阅是否顺手
- **Claude Code**：跨文件任务：规则是否持续生效
- **Antigravity**：界面任务：能否实际浏览验证

### 展开内容

## 42 · 国内外选型，留下四份可复查的结果

章节：四 · 版式：S19

位置：工具与模型选型 → 4.2 真实任务试用

### 投屏要点

- **设计题**：同一约束，比较取舍和遗漏
- **改动题**：同一缺陷，比较修复与回归
- **审查题**：预埋缺陷，记录漏报与误报
- **总成本**：费用 + 工时 + 返工 + 耗时

### 展开内容

- **固定任务与标准**：需求澄清、设计比较、缺陷修复、审查、失败恢复；同一仓库和验收条件。
- **分两轮比较**：固定环境看模型差异；允许产品完整流程看最终交付效果。避免混淆原因。
- **记录质量与成本**：重复运行；统计通过、漏报、误报、人工介入、耗时、费用与返工。
- **形成任务分工**：稳定主力做日常；已验证强项处理高难；专项工具做确定性检查。明确升级和切换条件。
- **业务语境**：中文表达、行业术语、隐含需求与边界；能否正确追问，而不是自行假设？
- **复杂设计**：备选方案、约束保持、成本取舍和失败推演；能否给证据与可实施设计？
- **跨模块编码**：仓库检索、调用链、影响范围、兼容与回归；是否只修了命名路径？
- **长任务与工具**：执行、恢复、状态维护和自我纠正；模型与工具适配是否稳定？
- **Review 与验收**：漏报、误报、可复现证据；能否发现已知业务、安全与一致性问题？
- **成本与条件**：延迟、可用性、配额、人工介入、数据与部署；算合格交付总成本。
- **本页的具体讲法**：设计题：同一约束，比较取舍和遗漏；改动题：同一缺陷，比较修复与回归；审查题：预埋缺陷，记录漏报与误报；总成本：费用 + 工时 + 返工 + 耗时

主讲备注：对 review 任务准备已知缺陷，对设计任务准备约束和验收要求。结果不要只比较代码长度。总成本可以按团队实际工时估算，必要时保留无法量化的风险。
不把“国内适合简单，国外适合复杂”预设为结论。可将这些任务作为假设，比较具体版本后说明哪组候选更合适。复杂设计、跨文件修改、长任务执行和高风险审查是检验额外成本是否值得的重点。

收束：选型最终回答：在我们的任务和约束下，哪种组合能更稳定地交付合格结果？

## 43 · 什么能并行，什么必须等？

章节：五 · 版式：S19

位置：多智能体协同 → 5.1 协同方式

### 投屏要点

- **候选调研**：不同方案可并行查证
- **需求到设计**：关键语义确认后再设计
- **独立审查**：规格 / 安全 / 恢复可分头查
- **代码整合**：统一版本，明确写入负责人

### 展开内容

- **串行交接**：需求 → 调研 → 设计 → 实现 → 验收；适合有明确依赖的工作。
- **并行分工**：独立候选调研、模块、测试或审查方向；前提是任务可独立验证。
- **主智能体协调**：分配任务、跟踪依赖、整合结果、处理冲突；仍要验证整体一致性。
- **交叉复核**：不同上下文或模型找反例、审查设计与实现；避免共同前提未经核验。
- **本页的具体讲法**：候选调研：不同方案可并行查证；需求到设计：关键语义确认后再设计；独立审查：规格 / 安全 / 恢复可分头查；代码整合：统一版本，明确写入负责人

主讲备注：多开几个聊天窗口不是自动协同。增加智能体会增加成本、延迟和整合负担。有依赖的决策不能盲目并行，模型投票也不能代替验证。

收束：按依赖、独立性和验证方式分工；角色名称不会自动产生能力。

## 44 · 给审查会话的交接包

章节：五 · 版式：S19

位置：多智能体协同 → 5.2 交接与执行

### 投屏要点

- **任务**：只审重试链路，不改代码
- **事实**：需求 v1 / 设计 v2 / 固定提交
- **交付**：场景 + 位置 + 影响 + 证据
- **收口**：实现者修复，审查者复验

### 展开内容

- **按已验证强项分工**：业务语义强的做澄清；研究强的核验来源；设计强的推演；工具稳定的实现；新上下文独立审查。
- **目标与边界**：任务目的、允许改动范围、非目标、前置依赖、失败报告方式。
- **共同事实与输出**：需求 / 设计版本、术语、接口、约束；交付格式、验证步骤、实际证据和未知项。
- **整合与裁决**：谁核验事实？谁处理分歧？谁整合和最终验收？不能只把几个总结拼在一起。
- **本页的具体讲法**：任务：只审重试链路，不改代码；事实：需求 v1 / 设计 v2 / 固定提交；交付：场景 + 位置 + 影响 + 证据；收口：实现者修复，审查者复验

主讲备注：同步案例中，需求会话确认重复请求语义，设计会话定义幂等和恢复，实现者落地，审查者独立注入超时并验证。业务取舍由人确认，错误前提不靠多个模型赞同变成事实。

收束：任务契约 + 版本化文档 + 独立验证，是可以立即采用的协作方式。

## 45 · 一个今晚就能用的协作方式

章节：五 · 版式：S19

位置：多智能体协同 → 5.2 交接与执行

### 投屏要点

- **A · 需求设计**：交付规则、图与阶段用例
- **B · 实现**：单一写入者，小步测试
- **C · 审查**：只读固定版本，报告反例
- **你 · 统筹**：确认取舍，跟进修复与放行

### 展开内容

- **会话 A：需求与设计**：检索候选；确认同步、重复请求与恢复语义。
交付需求、设计、图、阶段任务和验收用例；负责人确认。
- **会话 B：实现**：读取已确认版本，按阶段修改与测试。
交付差异、执行记录、未验证项；不擅自扩大范围。
- **会话 C：独立验收**：只读需求、设计、规范和固定差异。
分别检查规格与质量，复现重试问题，报告证据。
- **人 / 协调者**：核验报告和分歧，交 B 修复，再交 C 复验。
检查自己掌握关键路径，确认风险与交付；更新任务状态。
- **需求与调研**：候选、来源、确认需求、重点难点、边界、用例
- **设计与确认**：方案取舍、完整设计、图、阶段任务与验收
- **阶段实现**：一个写入者，小步开发和运行测试
- **独立验收**：规格、工程质量、关键风险并行检查
- **修复与放行**：核验问题、修复复验；人确认关键交付
- **本页的具体讲法**：A · 需求设计：交付规则、图与阶段用例；B · 实现：单一写入者，小步测试；C · 审查：只读固定版本，报告反例；你 · 统筹：确认取舍，跟进修复与放行

主讲备注：这是无需开发平台即可执行的方式。会话在同一工具或跨工具都可以；先手动交接文件。需要并行时，可增加只读审查会话，不先增加多个写入者。
同一工具内多个会话，或不同工具之间都能手动实现，不需先搭建编排平台。共享需求、设计、任务和验收文档，带版本；审查者只读固定版本，单一实现者修复，避免覆盖。

收束：每次交接携带版本、事实、边界、输出和验收标准，不只转发上一个会话的总结。

## 46 · 下一个项目，先试这四件事

章节：收束 · 版式：S19

位置：讨论与行动 → 6.1 下一次怎么做

### 投屏要点

- **需求**：把“不确定”写出来
- **设计**：用一个异常场景验方案
- **Review**：让新会话查规格和规范
- **自己**：亲手改一个关键规则

### 展开内容

- **价值如何保留**：主动发现问题、理解业务、学习判断，避免交付增长而理解退化。
- **研发如何掌控**：调研成熟能力，确认需求和设计，分阶段验证，掌握关键代码再放行。
- **协同如何落地**：按任务选工具与模型，用版本化文档交接，独立复核并明确责任。
- **先验收再执行**：开始就给目标、约束、输出、测试与通过标准；阶段完成同步状态。
- **先读现有再新增**：读取仓库、规则与已引入能力；外部调研有来源，避免重复实现。
- **事实与假设分开**：记录来源、日期、未验证项和决策人；Memory 保存稳定内容并定期清理。
- **小步改，小步 review**：控制任务和差异规模；每阶段可运行、可解释、可验证。
- **要求真实证据**：报告执行过什么、失败在哪里、没验证什么；出错先复现与根因定位。
- **保留自己的理解**：阅读关键路径、预测行为、调试和修改；复盘后维护 SKILL、规范、案例与术语。
- **本页的具体讲法**：需求：把“不确定”写出来；设计：用一个异常场景验方案；Review：让新会话查规格和规范；自己：亲手改一个关键规则

主讲备注：开放交流：你现在最失控的是需求、设计、代码还是验收？下一次使用 AI，愿意先改变哪一个环节？围绕具体任务和失败案例展开，不停留在工具排行榜。
不要求团队一次采用全部技术。可先改变一个环节：任务先写验收、实现后独立 review、放行前故障推演。看效果后再扩展，避免流程负担超过收益。

收束：你现在最想改进哪个环节？我们用一个真实任务一起推演。
